1. Overview

This document defines the observability and monitoring strategy for the MCBB 3.0 Multi-Cloud Backbone deployment. It covers what we intend to monitor, which metrics are collected at each layer, which tools collect and process them, and how those tools are integrated into a unified monitoring posture.

The strategy operates in two states — an interim state using AWS-native tooling deployed during the lab and initial production phase, and a target state built around a cloud-agnostic toolset that provides consistent visibility across AWS, Azure, and GCP.

The MCBB 3.0 environment spans the following components:

  • AWS Cloud WAN core network — 7 segments (Prod, Non-Prod, Shared Services, Hybrid, Inspection, MnA, Clients)
  • Cloud Network Edges (CNEs) in us-east-1, us-east-2, us-west-2, plus international regions (EMEA, APAC, India, LATAM)
  • 7 Direct Connect Gateways — 3 North American, 4 international (continental)
  • Inspection VPCs with Palo Alto VM-Series firewalls deployed via Gateway Load Balancer (GWLB)
  • Workload VPCs (Prod, Non-Prod, Shared Services) per region
  • Hybrid Edge — Cisco 8711 Edge Connect switches at Ashburn, Dallas, Chicago, San Jose colos
  • International DXGW tier — LATAM (sa-east-1), EMEA (eu-west-1, eu-central-1), India (ap-south-1, ap-south-2), APAC (ap-southeast-1, ap-southeast-2)
  • On-premises Core One WAN fabric

2. Design Requirements

The following observability Design Requirements (DRs) are formalized in the MCBB 3.0 design document and drive the monitoring scope:

DRRequirementPrimary Coverage
DR 3.1Real-time telemetry on active traffic flows using standard tools and API callsCloudWatch (interim) → ThousandEyes + Splunk (target)
DR 3.2Real-time SLA metrics reporting — latency and packet lossThousandEyes
DR 3.3Historical telemetry on network flows — top talkers, top requestors, fat flowsVPC Flow Logs → S3 (interim) → Splunk (target)
DR 3.4Performance metrics reporting via push, pull, or subscription mechanismsCloudWatch alarms (interim) → Selector AI (target)

The broader narrative requirement from the design document states: network telemetry must provide real-time visibility into traffic flows, top talkers, fat flows, and related metrics, and network-related data must be retrievable from CSP infrastructure to support internal capacity planning and alerting.

4. Monitoring Layers and Metrics

4.1 Direct Connect / Transit VIF Layer

Covers the physical DX circuits and Virtual Interfaces (VIFs) connecting Edge Connect colos to each regional DXGW or continental DXGW. Both North American and international DXGWs carry 2 VIFs per region. With only 2 active VIFs per DXGW, a single VIF failure represents a 50% capacity reduction before any failover action — making per-VIF health monitoring critical across all regions.

4.2 BGP and Routing Policy Layer

Covers BGP inbound and outbound prefix advertisement between DXGWs and CNEs, and the Cloud WAN routing policy that sets Local Preference (LP) values to enforce geographic DXGW preference per CNE.

LP assignments per design: CNE us-east-1 prefers DXGW-EAST (LP=300), DXGW-EAST-2 (LP=200), DXGW-WEST (LP=100). CNE us-east-2 prefers DXGW-EAST-2 (LP=300). CNE us-west-2 prefers DXGW-WEST (LP=300).

AWS References:

  • DX Routing Policies and BGP Communities
  • AWS Cloud WAN — DX Gateway Associations
  • AWS Network Manager Route Analysis

In the Centralized Egress pattern, the NAT Gateway in the Inspection VPC is the single egress IP profile for all spoke VPCs. Port exhaustion here impacts all spokes simultaneously.

For forensic source VPC analysis on port exhaustion events, VPC Flow Logs are forwarded to Splunk (via Kinesis Data Firehose or Lambda → Splunk HEC), where source VPC identification queries are run directly in Splunk.

4.7 VPC Flow / East-West Enforcement Layer

VPC Flow Logs are enabled on all production and critical VPCs to validate that spoke-to-spoke traffic is not bypassing the Inspection Segment, and to support historical flow analysis for DR 3.3. The Cloud WAN send-via policy must prevent any direct spoke-to-spoke path — Flow Log analysis in Splunk confirms this enforcement is working.

7. Alert Strategy

Alerts are organized into four severity tiers. Routing of alerts to the correct destination is subject to open decisions — see the Open Decisions page.

TierCriteriaResponseExamples
P1 — Immediate Service-impacting, no redundancy available Page on-call — respond within 15 minutes DX ConnectionState DOWN with no standby VIF; GWLB all targets unhealthy in a region; HA failover during business hours; NAT ErrorPortAllocation >0
P2 — Urgent Degraded redundancy, increased risk Alert on-call — respond within 1 hour Single VIF down (peer VIF absorbing all traffic); BGPPeerState not ESTABLISHED; Palo Alto session table >80%; BGP inbound or outbound prefix count drop
P3 — Warning Performance degradation, approaching threshold Ticket created — respond within 4 hours VIF bandwidth >85% provisioned; ALB p99 latency 2x baseline; ThousandEyes latency SLA breach; CloudWatch PacketsDropCount non-zero
P4 — Informational Operational visibility, capacity planning Dashboard / daily report Top talkers, fat flows, rule hit distribution, Forward Networks topology diff (no impact), Wiz posture findings (low severity)

8. Retention

Retention applies to the third-party SIEM, observability, and monitoring platforms that are the authoritative store for MCBB 3.0 telemetry. Final retention periods are subject to Fiserv Records Management and GCS compliance requirements.

ToolRetentionNotes
Splunk Per Fiserv SIEM retention policy Authoritative store for Palo Alto traffic/system/config logs, VPC Flow Logs, CloudWatch metrics, WAF logs, CloudTrail, and cross-CSP events. Hot/warm/cold tiering configured per Splunk cluster policy.
ThousandEyes 90 days (platform default) Path test results, latency baselines, and SLA metrics. Extended retention available via ThousandEyes API export to Splunk.
Forward Networks Per Forward Networks platform policy Topology snapshots and path compliance diffs. Historical snapshots configurable per deployment.
Wiz Per Wiz platform policy Security posture findings and misconfiguration events. Critical findings should be exported to Splunk for extended retention.
Selector AI Per Selector AI platform policy Anomaly events and RCA results. Significant events forwarded to Splunk as the long-term record.
